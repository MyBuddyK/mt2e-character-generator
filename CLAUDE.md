# Traveller (MT2e) Character Generator

A web app for players to roll Mongoose Traveller 2nd Edition characters together. The planned scope is
stepping through careers term by term and exporting to Foundry VTT (the JDR-Ninja `mgt2` system). It is
also the owner's portfolio project.

## Commands

- `npm run dev`: local dev server
- `npm run check`: lint (oxlint), typecheck (tsc), the conventions check (`npm run check:conventions`) and unit
  tests (Vitest). Run before every commit.
- `npm run test:coverage`: the unit tests with a v8 coverage report of `src/engine`, `src/storage` and
  `scripts` in `coverage/` (git-ignored). CI runs it and shows the totals on the run's summary page. No
  threshold is set.
- `npm run test:mutation`: Stryker mutation testing of `src/engine` (`stryker.config.json`, with
  `vitest.stryker.config.ts`, which leaves out the seed sweeps). Reports go to the git-ignored
  `reports/mutation/`. `.github/workflows/mutation.yml` runs it monthly and by hand;
  `.github/workflows/flaky.yml` runs the browser suite three times with no retries every week.
- `npm run test:e2e`: Playwright against a production build. In a sandbox with a preinstalled browser,
  set `PW_CHROMIUM_PATH` to its `chrome` binary.

## Layout

- `src/engine/`: rules logic as plain TypeScript, with no React imports. Every dice roll goes through
  `dice.ts`, so a seed reproduces a character. The only other randomness is `randomSeed` in
  `character.ts`, which picks a new seed. Store each value the generator decides as an
  `Overridable<T>`; that covers characteristics and every career roll and outcome.
- `src/data/careers/*.json`: career data. Every JSON file in that folder is checked against the zod
  `CareerSchema` in `src/engine/career-schema.ts` when it loads. Files that fail are left out and
  listed in `careerErrors`, which the app shows and a unit test checks.
- `src/engine/career-pack.ts`: career pack parsing, fingerprints, and the rule for which careers are listed
  when packs are loaded. `src/storage/`: localStorage and URL fetching for packs. `src/use-career-packs.ts`
  and `src/CareerData.tsx`: the pack state and the Career data section.
- `src/engine/species.ts`: the species schema, the built-in Human, and how species modifiers change the
  rolled characteristics. `src/storage/species.ts` saves the picked species per seed.
- `src/engine/terms.ts`: the career engine. `buildCareer` rebuilds a career from the seed, the player's
  choices and overrides, and the data; each roll uses `diceFor(seed, path)`. `src/engine/policy.ts`: the
  Finish career policy. `src/engine/effects.ts` and `src/engine/rules-schema.ts`: event effects and the
  `rules` values. `src/data/rules/sample-rules.json`: invented rules. `src/use-career.ts` and
  `src/Career.tsx`: the Career section; `src/storage/characters.ts` saves career input per seed.
- `scripts/`: `validate-pack`, `schema` (writes the git-ignored `public/career-pack.schema.json`) and
  `check-conventions` (see Documentation rules) and `coverage-summary` (the CI coverage table), run with tsx and typechecked by `tsconfig.scripts.json`.
- `src/engine/invariants.test.ts`: seed sweeps that run the same check on a fixed list of seeds, for rules
  that should hold for any seed (repeatability, characteristic ranges, how Finish career ends).
- `src/App.tsx`: UI.
- `e2e/`: Playwright specs. `e2e/accessibility.spec.ts` runs axe-core (WCAG A and AA rules) on eight page states. `e2e/fixtures/` holds invented career packs used by the specs and unit tests. `e2e/seed.spec.ts` is the starting page for the Playwright agents. Specs use
  relative URLs (`./?seed=x`) so they run under any `BASE_PATH`; CI runs them at `/` and at the Pages path.
- `specs/`: test plans from the planner agent. `docs/features/`: feature specs from `feature-designer`.

## Agents (`.claude/agents`)

- `feature-designer`: turns an idea into a feature spec with acceptance criteria.
- `playwright-test-planner` → `playwright-test-generator` → `playwright-test-healer`: Playwright's own
  test agents (plan, write, fix), using the MCP server in `.mcp.json`. These files were generated by
  `npx playwright init-agents --loop=claude` and then edited to follow this file. Re-running that
  command overwrites the edits.
- `playwright-test-monitor`: runs the suite, sorts failures into regressions, broken tests and flaky
  tests, and hands broken tests to the healer. On a green run it also removes duplicate or purgeable tests,
  following the rules in its file.

## Type checking

`tsconfig.app.json` and `tsconfig.node.json` set `strict` plus `noUncheckedIndexedAccess`,
`exactOptionalPropertyTypes`, `noImplicitOverride`, `noImplicitReturns` and
`noPropertyAccessFromIndexSignature`; `tsconfig.e2e.json` sets the same for `e2e/`. Don't loosen these,
and don't use `any`, `@ts-ignore`, `@ts-expect-error`, non-null `!` or `as` casts to get past them.
`.oxlintrc.json` makes each of those a lint error (`as const` is allowed), and also fails on skipped or
focused tests, tests with no `expect`, and two tests with the same title. `npm run lint` passes
`--deny-warnings`, so a warning fails it too.

## Documentation rules

These apply to code comments, test names, commit messages, PR descriptions, READMEs, feature specs and test
plans.

- Make no falsifiable statements. Describe only what the code does now. Don't claim performance, quality,
  coverage or behavior that the code or a test doesn't show. Mark planned work as planned.
- Every exported function, type and constant gets a comment that states what it does: its inputs, what it
  returns, and any side effects or edge cases.
- Every test (`it`, `test`) and `describe` block gets a comment or name that states what it checks: the
  setup, the action and the expected result.
- No self-congratulatory or evaluative language: no "robust", "elegant", "clean", "powerful",
  "comprehensive", "best practice", or similar.

`npm run check:conventions` (`scripts/check-conventions.ts`) checks the parts a script can find: an
exported declaration or a test block with no comment above it, a skipped, focused or todo test, and
phrases from its `BANNED_PHRASES` list. Whether a comment is accurate is left to review.

## Acceptance criteria and tests

Each acceptance criterion in `docs/features/` starts with an id: `PK-n` (career-import), `CT-n`
(career-terms), `CR-n` (career-rules), `TR-n` (term-removal), `SC-n` (seed-controls), `EC-n` (event-choices) or `SP-n` (species). A test that checks a criterion names it on the last line of its
comment, `// Criteria: CT-4, CT-6.` `npm run check:conventions` fails when a criterion has no id, an id is
used twice, a test names an id that doesn't exist, or a ticked (`[x]`) criterion is named by no test.
Don't renumber ids; add new ones after the last.

## Other rules

- Treat the repo as public. Never commit rulebook text or full tables. Career files hold short summaries and a
  `source` citation; the owner fills in the real data.
- Specs load the app with a fixed `?seed=` so results are deterministic.
- Never skip or delete a test to get green. Removing a test that duplicates another, or that checks
  removed behavior, is a separate change made only on a green run (see `playwright-test-monitor`).
